# ADR-0027：AccessAdapter 自适应轮询与 CPU 节能

| 状态 | 日期 | 决策者 |
|------|------|--------|
| 已采纳 | 2026-07-05 | 韵启龙 |

---

## 背景

`AccessAdapterBase` 是 FlowHub 接入层的基类，所有前端适配器（CliAdapter、WsAdapter 等）均继承自它。与 EO（由 CAF 框架调度、工作窃取线程池自动管理）不同，AccessAdapter 运行在自己的独立线程上（基于 `caf::scoped_actor`），框架无法干预其线程调度行为。

`AccessAdapterBase::run()` 的主循环交替执行两件事：

```
while (true) {
    readFrontend();                            // ① 等待前端输入
    receive_for(kPollTimeout, messageHandler_); // ② 检查 CAF 邮箱
}
```

如果两处都使用固定短超时（如 10ms），在无前端接入或用户长时间无操作的 idle 场景下，CPU 将持续空转——虽然每次唤醒消耗极小，但高频率累积后不可忽略。对于部署在嵌入式平台的场景（如树莓派），这会造成不必要的功耗和散热问题。

因此需要一种机制，在 idle 期间自动降低轮询频率，有交互时立即恢复。

---

## 决策

### 自适应 idle 退避策略

在 `AccessAdapterBase` 中新增一个计时器，跟踪"距离上一次前端活动"的时长。当前仅实现一档：

| idle 时长 | readFrontend poll 超时 | 效果 |
|-----------|----------------------|------|
| ≤ 30 秒 | 100ms（当前默认值） | 正常响应 |
| > 30 秒 | 1s | 深度睡眠，降低 CPU 占用 |

后期通过配置文件调整阈值与超时值。当前阶段硬编码。

**不改邮箱轮询间隔**。`receive_for` 的 sleep 间隔保持当前硬编码值不变。原因：邮箱轮询本身不构成 CPU 热点——`receive_for` 内部已有 `has_next_message()` 快速路径，无消息时 `sleep` 一次即让出 CPU。真正导致 idle CPU 空转的是前端 `poll` 的高频超时唤醒。

### 选择仅调整前端 poll

系统是请求-应答模型。存在两个可调超时点：

1. **`readFrontend` 的 `poll` 超时**：控制前端输入的空转时间
2. **`receive_for` 的 `sleep` 间隔**：控制邮箱检查的空转间隔

**选择仅调整 `poll`**，理由：

- **前端输入由硬件中断驱动**。用户按键 → 内核中断 → `poll` 瞬间唤醒。`poll` 的超时只在 idle 期间生效，**增大超时不劣化交互体验**。
- **邮箱轮询不构成 CPU 热点**——无消息时 `receive_for` 让出 CPU，不空转。改邮箱间隔无助于降低 CPU 占用。

### 计时器粒度为"距离上次前端活动"

活动定义为 `readFrontend()` 返回 `true`（有实际输入且被处理），而非 CAF 消息到达。因为 CAF 消息（尤其是广播类消息如 TaskSync）可能在多 Adapter 之间频繁触发，不应阻止 idle 退避。

---

## 备选方案

| 方案 | 否决原因 |
|------|----------|
| 同时调整 `receive_for` 的 sleep | 邮箱轮询不构成 CPU 热点，无必要 |
| 多级阶梯退避（4 档） | 当前阶段过度设计，后期按实测数据加入 |
| 用信号/SIGIO 完全替代 poll | 非所有前端类型都支持异步信号，移植性差，复杂度高 |
| CAF 框架层面统一调度 | 改动框架成本太高，且 CAF 设计上不管理外部 IO 线程 |
| 直接 `pause()`/`yield()` 线程 | 缺乏系统级计时，无法保证确定性唤醒 |

---

## 影响

- **`AccessAdapterBase::run()`**：需新增计时逻辑，根据 `readFrontend` 返回值更新最后活动时间，idle > 30s 时将 poll 超时从 100ms 切换为 1s。
- **各 Adapter 的 `readFrontend`**：需从基类获取建议的 poll 超时（当前硬编码 100ms）。
- **无前端接入场景**：多个 Adapter 同时 idle 时叠加省电效果最明显。
- 后期通过配置文件调整阈值与超时值，当前硬编码。
- 本 ADR 仅为设计决策记录，**代码实现待后续完成**。
